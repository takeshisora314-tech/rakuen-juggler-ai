# 楽園上新屋 ジャグラーAI

iPhone向けGitHub Pages用。機種別台割、公開実績と取得状況を表示します。
実験的な参考候補、事前保存、自動答え合わせと方式比較に対応しています。**実設定の推定・設定変更の確認はできず、予測精度は未検証です。学習済みAIではありません。**

## 事前予想と自動答え合わせ

`python forecast_engine.py`を収集後に実行します。実行は日本時間05:00、06:17（再実行）、23:30（GitHub側で遅延し得ます）。23時以降は公開済みの当日実績も取得対象とし、未公開なら翌朝に確認します。GitHub Actions/Pagesのみでは07:00公開を保証できません。

- 7時前：当日分を`history/forecasts/YYYY-MM-DD.json`へ一度だけ保存。排他的ファイル作成とSHA-256で改変を検知し、再実行しても予想を上書きしません。
- 7時以降：保存済みの当日予想は23時まで表示を維持します。当日予想がなければ翌日分を仮表示するだけで、遅れた当日予想を後付けしません。
- 新規予想には全条件適合台の`rankings`と従来の上位3台`strategies`を保存します。成績比較・方式切替は上位3台のまま固定し、従来の評価との混同を防ぎます。過去の予想は変更しません。
- 評価：保存済み予想の対象日・機種・台番に一致する実績のみ使用。未公開・欠損は「公開待ち」で、0や外れに置換しません。評価済みファイルは固定します。
- `history/evaluations/YYYY-MM-DD.json`へ、3方式別の公開差枚平均、プラス台数、対象条件を満たす全台平均との差、低稼働台数等を保存。実際の収支や設定上げ的中とは区別します。
- 過去データの時系列再計算は`data.json`内で「過去再計算」として分離し、事前予想実績や方式の自動切替には使いません。

### 実験ルール v1

対象日より前の14暦日内・最大7取得日を使用します。同じ機種ID・対象日有効の台番のみを扱い、3,000G以上の有効日が3日以上・総12,000G以上の台を対象とします。最新の機種実績が対象日の2日前より古い場合や、対象台が3台未満の場合は見送ります。新機種に旧機種の履歴を流用しません。

3成分は、凹み＝直近3有効日の差枚合計から`clip(-合計/4000,0,1)`、RB＝同機種平均へ5,000G分縮約したRB率の相対値から`clip(0.5+2*(相対率-1),0,1)`、稼働＝`min(履歴G/30000,1)`。重みはバランス型45/35/20、凹み型80/10/10、RB型20/70/10。点数は優先度であり確率ではありません。凹みからの反動や設定上げを保証する根拠ではありません。

初期はバランス型を採用し、他2方式も事前保存して並行評価します。事前保存された同条件の評価が30日以上そろってから直近最大60評価日の平均を比較し、同条件全台平均との差が既定方式より100枚以上改善し、プラス台率が悪化しない方式へ切り替えます。これは保守的な実験用ルールであり、統計的な優位性や毎日の精度向上を保証しません。

## 台別実績

直近7暦日以内について全機種を補完します。最新日以外は全台の数値が取得済みなら再取得しません。サイト負荷と実行時間を抑えるため、未完了の過去営業日を最大2日ずつ処理し、残りは次回へ回します。日付別ファイルを分け、異なる日を同一ファイルに混ぜません。画面の「実績日」で取得済みの日を選択できます。

直近3取得日の各日3,000G以上・差枚欠損なしの台に限り、差枚合計が低い順の3台を参考表示します。これは単なる過去実績集計であり、設定上げ予想・確率・期待収支ではありません。基準日当日以降の実績を使わず、機種IDをまたいで履歴を流用しません。予測精度の検証は未実施です。

`python collect_machines.py`は標準のPlaywright Chromiumでみんレポの楽園上新屋店を開き、回転数・BB・RB・差枚を取得します。公開表の列、台番、日付、店舗を検査します。想定台番の一部だけ掲載されている場合は検証済みの行だけを保存し、`partial`と`missing_numbers`で未取得台を記録します。台番重複・想定外台番・空表は拒否し、台割を自動変更しません。サイトの認証・アクセス制限は回避しません。

- `history/machines/YYYY-MM-DD/機種ID.json`：営業日別の実績。既存値を欠損で消しません。
- `data.json`の`machine_records`：直近90日分。古い履歴ファイルは削除しません。
- `machine_collection`：今回の試行日時、対象日、機種別の取得・未取得状況。失敗しても過去の取得値は残します。

画面は選択日以前の最新取得日を機種単位で表示します。日付と出典リンクを各台に明示し、未取得を0や予測値で補いません。みんレポの独自集計値は参考値であり、公式実績や勝利保証ではありません。取得の成否はActionsの緑色だけでなく`machine_collection`で確認してください。

## 公開先の監視

`python check_publication.py`はGitHub Pagesの実際の`data.json`を読み、当日分の固定予想・SHA-256・機種の網羅性・日時を検査します。予想の生成時刻が7時前であっても、公開先を7時前に観測できなければ「7時までの公開は未確認」とします。見送り機種も公開確認とは分けて表示します。

- 06:45 JST（21:45 UTC）・07:05 JST（22:05 UTC）は収集せず公開監視のみ。朝の収集後と手動実行後にも確認します。夜23:30には実施しません。
- `publication_status.json`: 最新の観測結果。`history/publication-checks/日付/時刻.json`: 上書きしない観測履歴。
- 同一予想IDを7時前に実際に観測した証拠だけを引き継ぎます。生成日時だけで公開成功にしません。7時以降に未公開・接続不能・整合性エラー等があればActionsを失敗扱いにします。通知の配信先や受信設定は構成していません。
- 監視結果のコミット自体にもPagesの公開遅延があります。07:00公開保証やSafari実機の描画テストではありません。

設定モデルの一次資料確認と設計の残作業は[MODEL_PLAN.md](MODEL_PLAN.md)に記録しています。

`python collect_sources.py`は次を保存します。

- `data.json`：最新の接続確認結果と、実行日の日本時間で有効な台割。既存の他のキーは維持します。
- `history/source-checks/YYYY-MM-DD/時刻.json`：実行ごとの接続確認結果。過去のスナップショットは上書きしません。

この履歴は**接続確認の履歴**であり、台別実績の履歴ではありません。
HTTP 200は台別の数値を取得できたことを意味しません。取得不可やタイムアウトを記録し、架空のデータで補いません。
収集ジョブだけに`contents: write`を付け、`data.json`と`history`のみをコミットします。
